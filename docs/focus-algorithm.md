# 对焦点分析算法说明

给一张 jpg，找出**这张照片对焦在哪里**。实现分两条互相独立的路线，**都跑、都上报**：

| 路线 | 读什么 | 回答的问题 |
| --- | --- | --- |
| **EXIF 元数据** | 相机写进文件的对焦点标签 | 相机*声称*它对在哪 |
| **内容分析** | 像素本身的清晰度分布 | 画面*实际*最锐利处在哪 |

两条一致时基本可以放心；不一致时两者都有可能是"对的"——元数据那一路可能是区域对焦
或手动对焦，内容那一路可能被画面里比焦点更锐的东西（噪点、纹理）带跑。所以程序从不用
一条去覆盖另一条，而是把两条都摆出来，并给一个"是否互相印证"的判断。

---

## 一、内容分析路线（传统图形学算法）

这条路线是纯像素算法，**不联网、不消耗额度、与相机型号无关，任何 jpg 都能算**。

### 1. 灰度 + 缩放（缩小时必须用 `INTER_AREA`）

先转灰度。如果最长边超过 `max_side`（默认 1024），等比缩小再算。

> **坑**：缩小必须用面积插值 `cv2.INTER_AREA`。用 `INTER_LINEAR` 会在缩放过程中
> 自己制造出高频分量，而下面整套算法就是靠高频分量判断清晰度的——等于自己往信号里
> 掺假。

### 2. 高斯去噪

σ 默认 1.0。

> **坑**：噪声也是高频。不去噪的话，传感器噪点和 JPEG 块效应会被当成"很清晰"，
> 峰值直接跑飞。这是对焦检测里最常见的翻车原因。

### 3. 清晰度图

对去噪后的图取**拉普拉斯绝对值**，再做局部求和（box filter）：

```
E(x, y) = |∇² I(x, y)|
S(x, y) = Σ  E(u, v)          # 在 (x, y) 周围 window × window 的窗口内求和
```

`window = clip(短边 × 0.08, 9, 129)`，取奇数。

这就是经典的 **SML**（Modified Laplacian / Sum of Modified Laplacian）清晰度评价函数，
和相机的反差对焦（contrast detection）用的是同一个原理。

也可以换成 **Tenengrad**（`--metric tenengrad`）：用 Sobel 梯度平方和代替拉普拉斯。
两者都实现、都可选，便于对比调参。

#### 为什么不需要额外的对比度归一化？

一个很自然的担心是：画面里本来就高对比的区域（天空-树枝边界、逆光轮廓）会不会
"天生赢"？

**不会，因为二阶导数天然拒绝失焦边缘。** 一片缓坡（失焦边缘）的一阶导数可以很大，
但二阶导数接近零。这是拉普拉斯算子固有的性质，不需要额外处理。

这一点是**实测确认**的，不是推理：`tests/test_focus_content.py` 里有一条回归用例，
构造"左半黑右半白再重度模糊（高对比但完全失焦）"＋"120/135 灰度差的小棋盘（极低对比
但锐利）"，SML 稳定选中后者，误差 0 像素。

> 早期版本确实加过一层"局部对比度归一化"（把清晰度除以周围的清晰度）。实测发现它
> 会把峰值推到清晰区域的**边界**上去（因为边界处"周围很模糊"导致比值虚高），
> 单像素定位偏差能到 40 像素以上。砍掉之后反而又准又简单。

### 4. 合焦区域

```
threshold = max( Otsu(S),  峰值 × peak_ratio )
mask      = S >= threshold
region    = 包含峰值的那个连通域（8 邻域）
```

**Otsu**（最大类间方差）在这里没用 `cv2.threshold` 的 OTSU 模式——那条路要求先把
浮点图压成 8 位，白白丢精度。代码里直接在浮点直方图上算，逻辑也更好读。

取 `max(Otsu, 峰值 × 0.5)` 是为了给"背景几乎全黑、只有一个亮点"这类极端直方图兜底：
Otsu 在这种图上会给出很低的阈值，光靠它会把整幅图都算成"合焦区域"。

相机的一个对焦点本来覆盖的就是**一片区域**（景深），不是一个几何点，所以区域是有意义
的输出，不是副产品。

### 5. 对焦点 = 合焦区域内的锐度加权质心

这是整套算法里最关键、也是**实测之后才定下来**的一步。

- ❌ **直接取"最锐的那个像素"（argmax）：很不稳。** 清晰区域内部本来就有起伏，
  单个像素的胜负几乎是随机的。合成样本上偏差 30~50 像素。
- ❌ **取区域的几何中心**：对均匀清晰区域没问题，但对"鸟的身体在焦点上、眼睛更锐"
  这种真实照片，会把结果拉到身体中心去。
- ✅ **取区域内以清晰度为权重的质心**：

  ```
  对焦点 = Σ(S·坐标) / Σ(S)      # 只在合焦区域的掩膜内累加
  ```

  既稳（是积分量，抗噪），又准（会被拉向真正最锐的地方）。同一批合成样本上误差 **0~1 像素**。

#### 但质心只在"区域确实是一片**实心**区域"时才成立

上面的做法有个前提：那片阈值区域是**一片实心**的合焦区域。真实照片里它经常不是，
此时质心会把人带偏。两条判据都是实测踩出来的：

**判据一 · 占比不能太大**（`max_region_for_centroid`，默认 0.25）

一张 OM-1 拍的两只伯劳（`PA052644.JPG`，蓝天背景）阈值区域占了 **43% 的画面**
（包围盒几乎整个 5184×3888），质心算出 (2837, 2734)，而真正的峰值在 (2830, 1883)
—— 差了 850 像素，输出里却还写着"最锐处大致在…"。占比超过四分之一就不再把这一大片
叫"合焦区域"（`region` 置 `None`），对焦点退回**最锐的那个点**。

**判据二 · 质心不能离峰值太远**（`max_centroid_offset`，默认 2 个聚合窗口）

真实照片阈值化之后，剩下的往往是**树叶边缘与枝条构成的稀疏骨架**。一张 OM-1 拍的
山斑鸠（`PA052737.JPG`）就是这样：区域只占 21%（没触发判据一），但骨架的加权质心
落在 **(4127, 2913) —— 一根明显失焦的树枝上**，而峰值在 1000 像素外的浆果上。
1:1 裁切对比一眼就能看出来：树枝是糊的，浆果上的果梗是锐的。

直接量"质心与峰值的距离"就能把两类情况分开，没有模糊地带：

| 案例 | 质心↔峰值 | 折合聚合窗口 | 结果 |
| --- | --- | --- | --- |
| 合成·清晰块 | 41 px | 1.4 | ✅ 采信质心（误差 0~1px） |
| 合成·失焦大边缘 | 51 px | 1.8 | ✅ 采信质心 |
| 真实·山斑鸠 | 1012 px | **3.3** | ❌ 改用峰值 |

> 也试过用"质心处的清晰度"来判，**判不出来**：清晰度图是窗口**求和**，质心旁边
> 有锐的东西就会把它的值抬起来 —— 那张落点在模糊树枝上的照片，该比值仍有 0.63。
> 也试过用"区域在包围盒里的填充率"来判，界限太窄（合成样本 0.55 vs 真实照片 0.50），
> 同样不行。

合成样本的清晰块只占 5%、质心离峰值 1.4 个窗口，两条判据都不触发，仍是质心路径。

### 6. 置信度

```
contrast   = 峰值 / median(S)
confidence = clip( log10(contrast) / log10(contrast_ref), 0, 1 )      # contrast_ref = 10
```

再用"合焦区域占画面比例"做惩罚：占比超过 60% 说明整幅图都"清晰"，
也就是景深极大或者整张都没对上焦，本来就没有明确焦点可言。

`confidence < min_confidence`（默认 **0.45**）时 `found = False`。0.45 对应
"峰值只比全图中位数高约 2.8 倍"。

**为什么定在 0.45**：这是拿一张真实 OM-1 鸟片（`PA052099.JPG`，5184×3888，
300mm f/6.7，树冠里的啄木鸟）校准的。那张照片在**所有分析尺度下**峰值/中位数
都只有 2.3~2.6，鸟处在全图第 98.5 百分位、但只是峰值的 78% —— 画面里到处
都一样锐，本来就不存在唯一对焦点。旧的默认值 0.2 会让这种照片"自信地"报出
一个贴边的坐标，那是误导。

**"找不到"不是"算失败"**：程序仍会算出并列出候选点，`detail` 里也写明最锐处
大致在哪、有多少处与之接近。信息一点不少，只是不再假装有一个确定答案。

### 可调参数

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `max_side` | 1024 | 分析时最长边缩到多少 |
| `denoise_sigma` | 1.0 | 去噪强度 |
| `metric` | `sml` | 清晰度评价函数（`sml` / `tenengrad`） |
| `aggregate_ratio` | 0.08 | 聚合窗口占短边的比例 |
| `peak_ratio` | 0.5 | 合焦区域阈值 = max(Otsu, 峰值 × 该值) |
| `top_n` | 5 | 上报的候选点个数 |
| `max_region_for_centroid` | 0.25 | 合焦区域占比超过它就不用质心、改用最锐点 |
| `max_centroid_offset` | 2.0 | 质心离峰值超过这么多个聚合窗口就改用最锐点 |
| `contrast_ref` | 10.0 | 峰值/中位数 达到该值记 1.0 置信度 |
| `min_confidence` | 0.45 | 低于此值就判为"没有唯一对焦点" |
| `region_quantile` | 0.75 | 区域评分取框内清晰度图的哪个分位数当"这块普遍有多锐" |
| `min_region_texture` | 3.0 | 框内灰度标准差低于此值 → "没有可测的细节"，判"无法判断" |
| `min_region_windows` | 2.0 | 框的短边至少要等于几个聚合窗口（否则标"不可靠"） |

#### 关于 `max_side` 的实测取舍

在 `PA052099.JPG` 上试了 1024 / 1536 / 2048 / 2592：

| max_side | 峰值位置（原图坐标） | 峰值/中位数 | 鸟处 = 峰值的 | 耗时 |
| --- | --- | --- | --- | --- |
| 1024 | (35, 1625) | 2.26 | 79% | 77 ms |
| 1536 | (33, 1623) | 2.34 | 79% | 91 ms |
| 2048 | (853, 303) | 2.48 | 77% | 106 ms |
| 2592 | (852, 308) | 2.57 | 78% | 118 ms |

**提高分辨率并没有让结论变确定**（比值一直在 2.3~2.6），只是让峰值在几个
差不多的候选之间跳来跳去 —— 这本身就是"没有主导峰"的证据。所以默认保持 1024，
需要时用 `--max-side` 调大。

## 二、EXIF 元数据路线

分三层，从最可靠的往下退。

### L1 · 标准 EXIF 标签（Pillow）

`SubjectArea` (0x9214) / `SubjectLocation` (0xA214) 是 EXIF 标准里的"主体位置"。
相当多的相机在单点对焦时会把对焦框写在这里，这是覆盖面最广、也最容易验证的一层。

取值按 EXIF 规范解释：

| 值的个数 | 含义 | 取哪个点 |
| --- | --- | --- |
| 2 | `(x, y)` | 该点本身 |
| 3 | `(x, y, d)` | 圆心 |
| 4 | `(x, y, w, h)` | 矩形中心 |

单位可能是像素，也可能是 0~1 的比例（不同厂商写法不一），用前两个值的量级判断。
像素写法还要按 `PixelXDimension / PixelYDimension`（EXIF 标称尺寸）换算，
因为标称尺寸和实际存储尺寸不一定相同。

离谱的值（越界太多）直接判为不可信 —— **宁可不说，也不给一个明显错误的点**。

### L2 · 厂商 MakerNote（ExifRead + 自解结构）

| 品牌 | 标签 | 状态 |
| --- | --- | --- |
| 富士 | `FocusPixel` (0x1023) | ✅ 直接就是图像像素坐标，最干净 |
| 佳能 | `AFInfo2` (0x0026) | ✅ 自解 uint16 数组；坐标以**图像中心为原点**，需换算 |
| 尼康 | `AFInfo2` (0x00B7) | ⚠️ 只上报"相机写了 AF 数据"，不换算坐标（见下） |
| 索尼 | `FocusLocation` | ⚠️ 私有坐标系，需要样张标定 |
| 其他 | — | 明确说明"暂不支持该品牌" |

> **为什么佳能要自己解**：ExifRead 的佳能解码把 `AFAreaXPositions` 这类**数组**
> 当成标量输出，只保留了每个数组的第一个元素——拿不到对焦点位置。所以这里从
> Pillow 的 MakerNote 子 IFD 取原始字节，按 uint16 数组自己解。
>
> **为什么尼康不换算**：尼康的 `AFPointsUsed` 是**网格位掩码**（不同机型是 51 点 /
> 39 点 / 21 点系统，网格列数和点序都不一样）。换算成像素坐标需要一份**按机型的
> 对焦点位置表**。在拿到真机样张之前，猜一份表出来的坐标是错的概率远大于对的概率，
> 所以这里只老实上报"相机记了 AF 数据、但本工具还不会换算"。

### L3 · 降级

三层都没有 → `found = False` + 一句具体的中文原因。截图、社交软件转存、部分手机照片
本来就没有 MakerNote，**这是正常情况，不是错误**。

### 朝向处理

先读 EXIF（此时图像还是**存储方向**），再用 `PIL.ImageOps.exif_transpose()` 转正；
读到的对焦点坐标按**同一组变换**映射过去，保证两条路线的坐标同源。

`apply_orientation()` 覆盖全部 8 种 Orientation，并且有一条测试**直接拿
`exif_transpose` 的实际输出当基准逐像素比对**——比手写期望值可靠（手写的那一版
一开始就写错了 4 个朝向）。

### 隐私

EXIF 里有 GPS 等敏感信息。本模块**只读白名单里的键**，对外只暴露
`make / model / tag / raw_value`，绝不把整个 EXIF 字典透传到 API、CLI 或前端。
这条由 `test_gps_is_never_leaked` 钉死。

## 三、区域清晰度评分（"选中的这一块有多锐"）

给一块矩形区域（典型来源：`whatbird detect` 框出的那只鸟、或用户在图上框选的一块）
评清晰度，回答**"这块是不是合焦的那块"**。

```bash
whatbird sharpness D:\photos\bird.jpg --box 120,80,300,240        # 像素框 x,y,w,h
whatbird sharpness D:\photos\bird.jpg --box-ratio 0.2,0.1,0.3,0.4 # 0~1 相对坐标
whatbird detect D:\photos\bird.jpg --sharpness                    # 检测 + 逐只评分，一步到位
```

### 只能给**相对**结论（这是本功能的边界，不是缺陷）

实测（同一张翠鸟照片逐级高斯模糊，模糊半径 0 / 1 / 2 / 4 / 8 / 16）：

| 高斯半径 | 框内锐度（绝对） | 全图峰值/中位数 | 框内最锐处 ÷ 全图最锐处 | 结论 |
| --- | --- | --- | --- | --- |
| 0（原图） | 41662 | 50.76 | 100% | 合焦 |
| 1 | 30916 | 37.08 | 100% | 合焦 |
| 2 | 17977 | 24.42 | 100% | 合焦 |
| 4 | 7388 | 12.76 | 100% | 合焦 |
| 8 | 2941 | 4.91 | 100% | 合焦 + "整张图清晰度差异不大"提示 |
| 16 | 1539 | 2.25 | 100% | **判为"图里没有明显的唯一锐处"**（不给结论） |

读法：

- **绝对锐度**（第二列）随模糊单调下降 → 只适合比"同一内容"的清晰/模糊两版；
- **相对量**（第四列）在同一张图里恒为 100% —— 因为整张图一起糊，最锐的地方还是那只鸟。
  所以**相对量测不出"整张照片都软"**：这一列回答的是"这块是不是画面里最锐的"，
  不是"这张照片清晰不清晰"；
- 整张图都软到峰值/中位数只有 2.25 时，`frame_has_peak` 闸门会拦住结论
  （判据与对焦分析的 `min_confidence` 共用，见 §一.6），并提示只能说百分位。

另外两条实测约束（都是**禁止跨内容比绝对锐度**的理由）：

| 场景 | 实测 |
| --- | --- |
| 同样模糊量下，棋盘格 vs 噪声区域 | SML 13847 vs 4518（**3.06 倍**）——"内容多"会被误读成"更清晰" |
| 纯色 / 天空区域 | 纹理 σ ≈ 1.1；同样模糊量下有内容的区域 σ ≈ 5.6；合焦的鸟 σ ≈ 36~48 |

**所以 API 只报同图内的相对量**（相对全图最锐处、全图百分位），跨照片比较需要基准标定，
本工具刻意不做。

### 三个主指标

| 指标 | 含义 | 判定用途 |
| --- | --- | --- |
| `relative_to_frame_peak` | 框内**最锐处** ÷ 全图最锐处 | ≥95% → 画面最锐的点就在框里 |
| `top_share` | 全图最锐的 1% 像素有多少落在框内 | ≥20% → 画面最锐的一片也在框里 |
| `percentile` | 框内 p75 锐度落在全图分布的百分位 | ≥75% → 比画面多数地方锐 |

> ⚠ 第一版把"框内 p75 ÷ 全图单点峰值"当主指标，**实测是错的**：合焦的翠鸟只得到 42%、
> 被判成"可能轻微失焦"，而且该比值在逐级模糊时反而**上升**（模糊先抹掉全图峰值）。
> 根因是两个量不可比（一块区域的稳健分位数 vs 单个窗口的极大值）。
> 现在一律"同量纲相比"：最锐处 vs 最锐处。

**`top_share` 是为了防单点噪声**：如果全图峰值恰好是一个孤立噪点，"最高只到 95%"会误判，
所以再看"那一片最锐的东西是不是也在框里"。

### 细节

- **聚合窗口必须远小于被测区域**。默认窗口（短边 × `aggregate_ratio` = 8%）是给
  "全图找唯一锐处"调的，对小鸟框太粗 —— 实测 810×1080 的图里一个 150×120 的框，
  窗口 61px，框只有 1.9 个窗口宽。所以区域评分**按框大小自适应选窗口**
  （`window = 框短边 ÷ (min_region_windows × 1.25)`，上限是默认窗口），
  并且**全图参照用同一个窗口重新算**（不同窗口下清晰度是不同量纲）。
- **"没有可测的细节"必须与"没对上焦"分开**：天空、纯色、虚化背景的 SML 恒接近 0，
  无论合焦与否。此时结论是"无法判断"，阈值取 `min_region_texture = 3.0`
  （纯色 ≈1.1 与"软但有内容" ≈5.6 之间）。
- **框小到连两个 3px 窗口都放不下**（分析尺度短边 < 6px）→ 标 `reliable=false`，只说"仅供参考"。
- 与对焦分析**共用同一条清晰度图管线**（`build_sharpness_map`）：缩放、去噪、算子、
  窗口口径完全一致，否则"全图最锐处在哪"和"框里锐不锐"两套口径没法比。

---

## 四、一致性判断

两条路线都给出结论时，判断它们是否互相印证：

- 有合焦区域时：看 EXIF 点是否落在区域里（带**半个区域尺寸**的容差——相机的 AF 框
  本身就是一片区域，不是几何意义的一个点）；
- 没有区域时：退化成"距离够近"（不超过画面长边的 5%）。

结果放在 `agree` 字段里。**不一致不是错误**，是值得看一眼的信息。

---

## 五、已知边界

1. **不判断"对焦点是否落在鸟身上"**。本功能不做目标检测，只回答"哪里最清晰"。
   一张背景树枝比鸟更锐的照片，算法会如实指向树枝。
2. **满是纹理的画面（树冠、草丛、花丛）里，SML 的判别力很弱**。这类照片里
   到处都是强边缘，"哪里最锐"和"哪里景深最浅"不是一回事 —— 此时程序会明说
   没有唯一对焦点，并列出候选点。
3. **整幅图都清晰（景深极大 / 风景小光圈）时不会有明确答案**，程序会明说找不到。
4. **尼康 DSLR 的网格 AF 点换算未实现**（见上）。
5. **索尼的 `FocusLocation` 私有坐标系未标定**。
6. **OM System（OM-1 等）的 MakerNote 未解析**：它的 MakerNote 用的是
   `OM SYSTEM` 私有头（不是标准 TIFF IFD），Pillow 与 ExifRead 都会直接跳过；
   对焦点藏在嵌套的 `FocusInfo` 结构里，需要按机型解码。实测 `PA052099.JPG`
   两个库都读出了 0 个 MakerNote 标签。
7. 只支持 `.jpg / .jpeg`（与项目第一版的约定一致）。

---

## 六、标注图的尺寸

`render_focus_overlay()` 默认把标注图缩到最长边 **2048** 以内（`max_side` 参数，
传 0 关闭）。原因很实际：一张 5184×3888 的原图直接画无损 PNG 是 **29 MB**，
编成 base64 约 39 MB —— 网页接口绝不该返回这个体量。缩到 2048 后是 4.6 MB 级。

**报告里的坐标始终是原图像素**，缩小的只是给人看的那张图；`render_overlay()`
通过 `coordinate_scale` 把坐标和标记尺寸一起等比换算，所以标记仍然落在正确位置
（有测试专门验证这一点）。

**"没有唯一对焦点"时，图上仍会标出最锐的那一点**（空心圆 + `SHARPEST`）：
结论是"没有一个确定的焦点"，但用户仍然需要知道画面里最锐的地方在哪。
候选点也都会以小圆点画出来。
